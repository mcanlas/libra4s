⚖️ libra4s

A local browser tool that helps Scala developers understand generated code by connecting one source snippet to structured compiler phases and JVM disassembly.

product frame

🎯 Primary job

Move quickly from a small Scala snippet to an understandable view of what the compiler and JVM toolchain generated.

Compiler phases and disassembly are complementary views of generated code, not separate products.

👩‍💻 Primary audience

Scala developers learning compiler transformations, investigating generated members, or explaining JVM output without repeatedly assembling local shell commands.

goals

✨ Product outcomes

  • Make generated Scala and JVM output approachable from one browser screen.
  • Preserve exact tool output while adding structure that improves scanning.
  • Represent compiler and disassembler failures honestly without discarding useful output.
  • Keep repeated exploration fast, deterministic, and eventually cacheable.
  • Support future option controls and snippet comparison without weakening the single-snippet flow.
  • Keep local development simple and avoid hidden client-side parsing rules.
shipped experience

✅ Current product behavior

📝 Input and execution

  • One Scala source textarea and one explicit Run action.
  • Editing triggers compilation after a 2000ms debounce.
  • Manual Run submits immediately and clears any pending automatic submission.
  • Overlapping requests use last-request-wins rendering; stale responses are ignored.
  • The last successfully compiled source is saved and restored through local storage.

⚙️ Compiler stage

  • Runs scalac -Vprint:all -color:never against a temporary source file.
  • Returns a structured success or process-error attempt.
  • Parses compiler output into collapsible phase sections.
  • Shows the compiler stage state in the compiler pane header.

🔍 Disassembly stage

  • Finds generated class files recursively under the compiler output directory.
  • Runs javap -c for each discovered class file.
  • Preserves class-specific output and process failures.
  • Shows success, failure, running, or skipped state in the disassembly pane header.

🚦 Failure behavior

  • Compiler and disassembler attempts have explicit success and failure shapes.
  • Compiler failures render exit code and captured lines in the left pane.
  • Disassembly is visibly skipped when compilation produces no usable class file.
  • The global running indicator is distinct from final stage results.
structured generated output

🧩 Member grouping and highlighting

Server contract

  • Successful stage payloads use ordered semantic groups rather than legacy raw stage-level line fields.
  • Every group retains an ordered List[String]; flattening groups reconstructs the original output.
  • Compiler roles are plain, def, val, and var.
  • Javap roles are plain, field, and method.
  • Compiler and javap role hierarchies remain separate.

Parser boundary

  • CompilerMemberGroupParser.scala owns compiler declaration parsing.
  • JavapMemberGroupParser.scala owns javap member parsing.
  • Each recognized declaration or member starts a separate group.
  • That group consumes subsequent blank lines and lines indented deeper than its declaration line.
  • Nested declaration-like text inside an owned body is not parsed again.
  • Unrecognized lines fail soft into plain groups; no output is dropped.
  • Constructors are represented as javap methods through their ordinary signatures.
  • Static initializers remain plain; no dedicated init role exists.

Visual treatment

  • JavaScript renders one element per server-provided group and does not classify output text.
  • Semantic colors are defined only in CSS.
  • Compiler mapping: def green, val red, var yellow.
  • Javap mapping: field yellow, method blue.
  • plain groups have no colored background or edge.
  • Consecutive groups of the same role alternate full and faded variants of the same base color.
  • The full/faded sequence resets when the semantic role changes.

Verification fixtures

Parser tests use compact compiler and javap excerpts derived from case class Dog(n: String). The fixtures make the relationship between emitted lines and semantic groups reviewable without running the web server.

constraints and non-goals

🛑 Boundaries

Required constraints

  • Keep command execution and filesystem behavior in libra4s-core.
  • Keep HTTP, response shaping, parsers, and browser assets in libra4s-web.
  • Preserve exact output ordering and content.
  • Keep parsing server-side and rendering declarative.
  • Keep compiler and disassembler cache identities separate.
  • Treat command execution as a security boundary before hosted deployment.

Explicit non-goals

  • Arbitrary multi-file builds.
  • A public hosted compiler sandbox without security work.
  • Replacing IDE diagnostics.
  • Reference-occurrence semantic highlighting.
  • Multiple saved browser drafts.
  • Every scalac or javap option.
  • A dedicated constructor or static-initializer role in the current grouping model.
architecture decisions

🏗️ Stable decisions

Layout Compiler phases remain on the left; javap output remains on the right.
Attempt model Stage status is derived from structured success or process-error attempts rather than duplicated flags.
Persistence Source saves only after successful compilation; future option selections save immediately as preferences.
API rollout Structured grouped fields replaced legacy success-level raw line fields directly.
Parsing Indentation-owned declaration blocks supersede contiguous same-role run grouping.
Color Semantic role colors supersede positional round-robin palettes.
Options Compiler and javap option sets must be researched before controls are added.
Caching Compiler and disassembler hashes must be separate because their inputs and future options differ.

next task definition

🔐 Deterministic caching foundation

If caching is the next milestone, the first implementation slice should define explicit stage-specific input models without enabling cache reads or writes.

  • The compiler input includes source text and compiler-relevant option state.
  • The disassembler input includes source identity, compiler option state, and javap option state.
  • Current fixed/default options are represented explicitly so later option controls do not silently change hash meaning.
  • Canonical strings carry schema/version prefixes.
  • Tests prove deterministic equality and sensitivity to relevant input changes.
  • JSON cache storage maps typed keys to separate typed values.
  • Cached compiler successes preserve generated class artifacts so javap can run without invoking scalac again.

This contract assumes the compiler and disassembler pipeline is deterministic for the same source and option inputs. Class-file content identity is therefore unnecessary for cache correctness.

settled product decision

🔑 Source-derived disassembler cache identity

Key disassembler results from source identity, compiler option state, and javap option state. The pipeline inputs are assumed to be complete and deterministic, so the cache does not inspect or hash generated class-file bytes.
